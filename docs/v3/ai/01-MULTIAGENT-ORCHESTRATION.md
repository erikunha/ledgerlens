# Multi-Agent Orchestration and Durable Runtime - Technical Specification

## Objective

Produce a **measurable** comparison between one-agent and multi-agent approaches for payment investigations while maintaining hard data boundaries. Multiagent is an experimental architecture, not the default baseline, unless paired evaluation demonstrates a real advantage.

## Orchestration families to implement

| Family | Definition | Useful comparison |
|---|---|---|
| Deterministic workflow | Fixed branch/DAG from validated typed input | Cheapest, predictable baseline |
| Single tool-calling agent | One LLM decides among safe tools | Existing ReAct baseline |
| Supervisor → specialist tools | Supervisor retains synthesis; limited delegated subcalls | Narrow specialist tasks, shared rules |
| Handoff | Routing sends case to role-specific active agent | Simpler intents with distinct instructions |
| Parallel fan-out + verifier | Independent FX, policy, ledger investigations join | Latency/coverage with careful evidence union |
| Generator → critic/validator | Candidate answer independently checked | Hallucination sensitivity; avoid consensus theater |
| Debate / council | Multiple proposals under strict budget with adjudication | Research only; quantify cost/false confidence |
| Map-reduce batch | Per-case investigations aggregated by code | Workload simulation and cost scaling |
| Adaptive router | Decision model chooses pipeline based on complexity/risk | Cost-quality frontier |
| Durable human checkpoint | Graph pauses for authorization or review then resumes | HITL, idempotence and rollback |
| Tool-oriented MCP integration | Typed local tools as MCP capabilities | Interop; never bypass API policy |
| A2A simulation | Mock external specialist with signed identity and timeouts | Protocol and trust boundaries only |

## Runtime state machine

`created -> validated -> planned -> executing -> evidence_join -> verification -> (needs_review | complete | failed)`.

Every state has `run_id`, actor, effective data scope and version, monotonic sequence, time, outputs, immutable artifact references. Human approval is `needs_review -> reviewed -> resumed` via a distinct authorized request, never generated by the agent itself.

## Delegation contract

```text
Dispatch(spec_id, task, branch_id, evidence_scope, allowed_tools,
         deadline_at, max_model_calls, max_tokens, max_usd, parent_run_id)
  -> {status, structured_payload, evidence_refs, spend, audit_ref, errors}
```

A subagent cannot widen `account_scope`, `branch_id`, tool rights or budgets beyond its parent. The dispatcher intersects rather than unions permissions. Model outputs are untrusted input until validated. Evidence references must resolve to immutable origin records; no free-form 'citation strings' count as verified references.

## Joining and conflict handling

- Join multiple reports only by typed evidence IDs and snapshot version; do not merge contradictory facts by majority vote.
- Conflicting amounts/FX dates/policy versions cause deterministic reconciliation or escalation.
- If one specialist times out, return partial status with explicit missing scope; never fabricate a success.
- Retry only read-only idempotent tools, capped to two attempts with jitter and deadline; no infinite tool loops.
- Cancellations stop new tool calls, close spans and mark incomplete claims.
- `budget_exceeded` is a normal, testable terminal outcome; no automatic additional provider spend.

## Human supervision

Present *what is being asked*, relevant sources, exact proposed action, alternatives, red flags and estimated cost/risk under the scenario assumptions. Reviewer identity must not be generated by the model. Public visitor can approve **sandbox-only** state transitions; it is never evidence of a real operations decision.

## Evaluation protocol

Compare D/E against existing C on same scenario snapshots, at least three independent provider runs per case initially; add uncertainty intervals and enough cases for statistically meaningful claims before claiming superior quality. Measure: correctness, claim-level supported/unsupported, false negative/positive escalation, cost-per-correct, tool trajectory, p50/p95, critical path, review burden, unsupported actions, cross-account access attempts, recovery after interruption.

## Reproducible tests

- Supervisor delegates only to allowlisted specialist with scoped account.
- Two independent tasks parallelize; overall duration reflects slowest critical path, cost includes both calls.
- Specialist invents evidence ID -> join refuses it.
- Two specialists disagree on settlement net -> deterministic calculator wins or escalates; no voting over arithmetic.
- Infinite recursion prevented by depth, call-count and spend caps.
- Retry idempotency holds after restart and duplicate event.
- Cancellation persists with partial tree; rerun uses explicit new run ID.
- Concurrent visitors never share chat model, cache, memory or ledger branch.
